# 重构方案：以声音为主导的多模态检测

- 日期：2026-11-24
- 状态：方案待确认。第 0 阶段（今晚前）已完成，其余阶段尚未开始。
- 依据：[调研报告](调研_高星切片与视频监控项目.md)（EVO-011），以及本文"实测依据"一节的测试数据。

## 一、为什么要重构

1. **只靠弹幕，证据太单一。** 调研的 7 个切片项目都以主播说的话为主干，声音（笑声、喊叫、音量）是第二大证据。我们现在只有弹幕、点赞、礼物三类信号。
2. **弹幕比内容晚。** Gus 直播间 +200 秒主播喊"哎哟真也输了我去 / OH MY GOD"，那两秒是 10 分钟里最响的；弹幕 +205 秒才开始刷"？"。
3. **弹幕看不到的笑点会漏。** 天霸直播间 +60～86 秒声音分类认出几处明显的笑声，弹幕检测因为开头 90 秒在热身，根本没看到。
4. **代码结构撑不住多路信号。**
   - `collect.py` 已有 695 行，录制、采集、检测、保留策略全挤在一起；
   - `heat.py` 的四个通道写死为弹幕类信号；
   - 实时采集和离线回放各自维护一套每秒循环。

## 二、几条原则

- **声音为主，弹幕为辅，画面兜底。** 按品类加权，搞笑和游戏属于"反应型"：语气、笑声、弹幕权重高，画面权重低（hotclip `MOMENT_WEIGHTS.reaction`）。
- **便宜的每秒都算，贵的按需调用。** 音量、说话检测、转写、声音分类都在本机跑；GLM 只做低频的场景理解和最后的精判。
- **实时和离线共用一个每秒引擎。** 采集时把每秒的感知结果落盘，离线回放直接读，结果可复现；改了模型或参数，再从整场音频重算。
- **时间由信号和句子边界给，模型只选编号。** 保持 FR-6.5。
- **每个阶段结束都能端到端跑通。** `python3 -m zhibo demo` 通过，用真实数据回放对比，写演化记录。

## 三、目标架构

```
每个直播间
 ├─ dyhub 弹幕 SSE ───────────────→ 弹幕感知：人数、笑点词、"？？？"、复制粘贴串、反应分类
 └─ ffmpeg（一路输入，三路输出，时间天然对齐）
     ├─ 原画 10 秒小段 → 环形缓冲（即时重放，已有）
     ├─ 整场音频存档 audio_*.ts（第 0 阶段已加）
     └─ 16 kHz 单声道 PCM 管道 → 声音感知
          ├─ 每秒音量、相对突变、短促爆发密度、噪声度
          ├─ 说话检测（silero VAD）+ SenseVoice 转写 → 带时间的逐句稿
          └─ 声音分类（AudioSet 527 类）：笑声、尖叫、欢呼、掌声、枪声、爆炸、音乐
   （可选）GLM 场景理解：每 60 秒一张九宫格 + 最近一分钟逐句稿 + 弹幕摘要 → 场景标签、有趣度
                     ↓  每秒一行"感知记录"，落盘 perception/<room_id>.jsonl
 融合检测：各通道按本直播间最近 N 分钟的百分位归一化 → 按品类加权 → 多路共振加分、整场常亮降权
          → 弹幕按滞后秒数前移后再参与融合
                     ↓  开始 / 结束（沿用"同时安静 40 秒才算结束"）
 归因：福袋、PK、刷屏、内容驱动（现有规则 + 逐句稿关键词，例如"福袋""PK""上链接"）
                     ↓
 即时重放：先占住，确认结束后往回存 5 分钟（已有）
                     ↓  直播后
 精判：5 分钟候选按逐句稿的句子切段（静音边界兜底）
       → 证据包 = 逐句稿 + 事件时间线文字 + 九宫格截图 + 弹幕
       → GLM 只回答铺垫、高潮、反应各是哪几句 → 多个候选放一起排序
                     ↓
 出片：裁切 + 自检（已有）+ 逐句稿字幕
```

## 五、依赖

- 核心（合成数据 demo、离线回放读已有感知记录）仍然只用标准库加 FFmpeg，系统 Python 3.9 就能跑。
- 声音感知需要项目自己的 `.venv`（已建好）：sherpa-onnx 2.0.3（Apache-2.0）、numpy 2.0.2。

  | zipformer-small-audio-tagging（2024-04-15） | 解压后 int8 27 MB / fp32 92 MB | 声音分类 |

## 六、数据集格式的变化

- 新增 `audio.json`：整场音频（第 0 阶段已加）。
- 新增 `perception/<room_id>.jsonl`：每秒一行，包含各通道的原始值，例如 `{"t":..., "db":-13.4, "spike":..., "burst":..., "laugh_tag":0.54, "scream_tag":..., "gun_tag":..., "speech":1, "chat_users":12, "laugh_users":5, "q_users":7}`。
- 新增 `transcript/<room_id>.jsonl`：每句一行，`{"start", "end", "text"}`。
- 旧数据集没有这些文件时，可以用 `python3 -m zhibo perceive --data <目录>` 从录像或音频补算出来。

## 八、实测依据（第 0 阶段，2026-11-24）

**测试样本**：`data/test10` 的三段录像（天霸、Gus、一乐店长，各约 10 分钟，720p 录像里的声音），机器是 Apple M1、8 GB 内存。

| 项目 | Gus | 天霸 | 一乐店长 |
|---|---|---|---|
| 音频时长 | 603 秒 | 602 秒 | 594 秒 |
| 说话检测 | 2.4 秒 | 2.3 秒 | 2.4 秒 |
| 转写 | 111 句，4.5 秒 | 83 句，3.5 秒 | 161 句，6.7 秒 |
| 声音分类（每 2 秒一窗） | 8.3 秒 | 8.4 秒 | 8.2 秒 |
| 合计、实时倍数 | 15.2 秒，39.7 倍 | 14.2 秒，42.5 倍 | 17.3 秒，34.3 倍 |
| 声音分类认出的笑声 | 无明显笑声 | 60、66、86、144 秒等处，概率 0.38～0.54 | 无明显笑声 |
| 其他 | 枪声 12 窗 | 枪声 11 窗 | 音乐 216 窗 |

- 三个模型全部加载后，进程峰值内存 622 MB。
- 单个直播间实时倍数 34～42 倍，三个直播间同时跑大约只占一个 CPU 核的十分之一【待验证：实时管道下的真实占用】。
- SenseVoice 的情绪和事件标签在这 355 句上全是"中性 / 说话"，**没有区分度**，笑声改用声音分类模型来认。
- 转写质量：能听出大意。Gus 的中英夹杂识别得比较乱，但"OH MY GOD""I'M SO HUNGRY"这类喊叫都转出来了，弹幕热词"饿了"正是在接"HUNGRY"这个梗。
- 声音领先弹幕的一个例子：Gus 直播间最响是 +200、+201 秒，弹幕 +205 秒才开始放量，相差约 5 秒（只有这一例，滞后要用今晚的数据统计）。

## 九、风险和待验证

- 【待验证】在吕德华、陈泽、coke 身上，笑声分类和转写的效果如何。今晚的整场音频就是测试材料。
- 【待验证】主播开麦唱歌、放背景音乐时，音量和笑声通道会不会一直亮。计划用"整场常亮降权"处理，并且只在音量过门槛时分类（frigate 的做法）。
- 【待验证】声音分类模型认的是主播的笑声，认不出观众；观众的笑只体现在弹幕里，所以两路要互补。
- 实时接入后，录制进程多了一路 PCM 输出。ffmpeg 出问题时要保证画面录制不受影响，计划让 PCM 管道读空时自动重启。
- 引入 AGPL 代码后，仓库整体按 AGPL-3.0 发布。
