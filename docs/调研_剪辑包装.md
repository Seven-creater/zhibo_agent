# 调研：把切片剪成"更吸引人"的成片

- 日期：2026-11-25
- 起因：系统已经能找到用户认可的笑点片段（EVO-023）。用户的下一个目标是让模型自动分析怎么剪，让成片既保留笑点，又能吸引观众。
- 方法：
  1. 重新细读之前拉下来的 hotclip、clips-studio 里与剪辑包装相关的代码和文档；
  2. 用 `gh search repos` 按星数补搜剪辑类项目，新拉了 6 个，浅克隆到 `third_party/research/`，只读代码和文档，不运行；
  3. 核对本机 ffmpeg 的能力。
- 说明：标【引用】的数字来自对方项目文档（多为对方转述的行业资料），我们没有复测。

## 一、结论（大白话）

1. **这个方向对，而且是现在差距最大的一块。** hotclip 自己的调研结论就是：选段做得再好，成片"包装层"（字幕、开场、声音、节奏）没做，看起来就不像能直接发的视频【引用】。我们现在出的片子只有裁切 + 可开关的字幕轨，包装几乎是空白。
2. **成熟项目的做法是"规则引擎 + 模型出方案"，不是"模型直接剪"。**
   - 模型负责判断：哪句做开场钩子、标题怎么写、哪个词要高亮、笑点在哪一秒、用什么布局；
   - 程序负责把这些判断变成确定的画面和声音：放大多少、音效放哪一帧、字幕放在屏幕哪里。
   - OpenShorts 让 Gemini 直接写 ffmpeg 滤镜字符串，结果代码里专门写了"清洗 AI 写坏的滤镜"的函数（`editor.py` 的 `_sanitize_filter_string`），说明这条路容易出错。
   - video-alchemy 的说法最清楚："剪辑方案就是数据，不是拖时间线"：模型写 JSON，程序照着剪。
3. **吸引眼球的手法有一套公认清单**：开场钩子、动态字幕、竖屏构图、笑点处推近镜头、音效和 BGM、紧凑节奏、封面和标题。每一项都有现成的实现和参数可以借（见第三节）。
4. **出片有两条路，建议都做：**
   - **A. 本地全自动出成片**：适合批量、无人值守。但本机 Homebrew 的 ffmpeg 9.0.2 没有字幕和文字滤镜（libass、freetype 都没编进去），要先解决"怎么把字印到画面上"；
   - **B. 生成剪映草稿**：用 pyJianYingDraft（Apache-2.0，5000 星）或 capcut-cli（MIT）。模型把字幕、花字、贴纸、音效、转场都放好，用户在剪映里打开还能逐轨修改，正好对上中文切片圈"AI 初剪 → 剪映精修"的工作流。限制是 Mac 版剪映能不能直接打开、导出这些草稿还不确定（【待验证】）。

## 三、"吸引眼球"的手法清单（我们能借什么）

| 手法 | 怎么做 | 参数和来源 | 对搞笑切片的意义 |
|---|---|---|---|
| **开场钩子** | 把片内最炸的一句或一个画面剪到最前面（1～3 秒），再从头播；或者只闪现 0.3～1 秒的结局画面 | hotclip `coldopen.ts`：钩子 1～3 秒、超过 3～4 秒就掉人；"全网仅 0.04% 切片有画面钩子"【引用】 | 很大：比如 Gus 片子开头先闪一下"I'M SO HUNGRY"，再从头播 |
| **标题贴片 / 钩子文字** | 开头几秒在画面上方压一行大字，比如"德华骂人骂一半突然秒怂" | OpenShorts `hooks.py`、hotclip `titleCard`；80～85% 的人静音刷视频，文字和口播要双保险【引用】 | 大：GLM 已经给出了 `title`，直接能用 |
| **动态字幕** | 中文主流是"一屏一短句 + 关键词换色或放大"，每句高亮不超过 1 个词；字幕放在画面高度 62～72% 的位置，避开平台按钮 | hotclip `subtitle.ts` 和调研第五点六节【引用】 | 大：笑点那个词（"hungry""太脆弱"）可以高亮 |
| **竖屏构图** | 游戏直播：主播摄像头放上面、游戏画面放下面（"先看反应，再看原因"）；其他情况用人脸追踪，或者原画居中、上下用模糊背景铺满 | clips-studio 的 11 种布局；OpenShorts 的 TRACK / GENERAL 两种模式 | 很大：吕德华、陈泽都是游戏画面角落叠一个摄像头小窗，直接裁成竖屏会裁掉一半 |
| **镜头推近** | 笑点那一刻快速推近（snap zoom），平时缓慢地呼吸式推拉；**推近必须对上真实事件**，随机推近反而招差评 | hotclip `autozoom.ts`（zoompan）、调研第三节【引用】 | 大：我们有笑声和音量突增的时刻，正好用来定推近时机 |
| **音效** | 每条最多 3～5 个：笑点落地放"叮"或综艺音效，硬切处放"嗖"，字幕上屏放"啵" | hotclip `sound-design.ts`：音效用 ffmpeg 本地合成，没有素材版权风险【引用】 | 中：综艺感，但多了显得廉价 |
| **BGM** | 比人声低 15～20 dB，人声出现时自动压低（sidechain），结尾淡出 | hotclip `sound-design.ts`、`bgm-ai.ts`【引用】 | 中：游戏直播本身声音很满，可能不需要 |
| **节奏** | 去掉停顿和口头禅；**笑声、情绪事件前后 1 秒不删**，保住包袱前的停顿；有意义的画面变化间隔不超过 3～5 秒 | hotclip `fillers.ts`、调研第三节【引用】 | 中：我们的片子已经是精剪的十几秒 |
| **封面** | 选片内音量最高、表情最夸张的一帧，再压上标题 | hotclip `cover.ts`：惊讶 / 激动表情的封面点击率高 20～30%【引用】 | 中：发布时用 |
| **一片多版** | 同一条片子做 2～3 套不同的标题、钩子、封面 | hotclip `variants.ts` | 以后做 A/B 测试用 |

**明确不建议做的**（hotclip 调研结论【引用】）：
- AI 生成 B-roll：口碑最差，直播切片以真人画面为主，用不上；
- 刻意去重、混剪、绿幕伪造在场：平台打击对象；
- 拿"爆款分"当绝对承诺：只能在同一场直播里用来排序。

**合规提醒**【引用，待核实】：
- AI 生成的配音、封面等内容需要显著标注，依据是《AI 生成合成内容标识办法》（2025-09-01 起实施）；
- 切片授权越来越严格，保留原始片段和分发记录有用。我们手里本来就有源文件和精确时间戳，留证成本很低。

## 四、模型怎么参与"决定怎么剪"

建议做法：第 5 阶段的判定已经输出了 `title`、`punchline`、`key_quote`、`cut`；包装阶段再让模型输出一份**剪辑方案 JSON**，程序照着渲染。方案里只放模型擅长判断的东西，并且都用句号、关键词指代，不让模型报时间戳、写滤镜：

```json
{
  "layout": "facecam_top_game_bottom",
  "hook": {"type": "flash_forward", "sentence": 39},
  "title_text": "想说生气，结果喊成了我好饿",
  "highlight_words": ["HUNGRY"],
  "zoom_at": [{"sentence": 39, "kind": "snap"}],
  "sfx": [{"sentence": 39, "kind": "ding"}],
  "cover_hint": "主播喊 HUNGRY 的那一刻"
}
```

程序这一侧：
- 句号换成时间；
- 推近的幅度和时长、音效的音量和间隔、字幕位置，都按规则参数来；
- 做完自检：钩子说的内容必须在片子里真的出现（hotclip 的"钩子兑付校验"）、片子总长度、音画轨。

这样，模型出错时最多是"选错了句子"，不会出现"写坏滤镜导致出不了片"。和现在的"只报段号、句号"原则一致（FR-6.5）。

## 五、两条出片路线

| | A. 本地全自动出成片 | B. 生成剪映草稿，人工精修 |
|---|---|---|
| 做法 | ffmpeg 合成：竖屏布局、推近、字幕、标题、音效、BGM | pyJianYingDraft 或 capcut-cli 写草稿：素材、字幕、花字、贴纸、音效、转场都放好 |
| 优点 | 无人值守、可批量；结果可复现；不依赖剪映 | 能用剪映的花字、贴纸、音效库，效果上限高；用户能逐项改；符合"AI 初剪 → 剪映精修"的习惯 |
| 缺点 | 包装效果全靠自己写；**本机 ffmpeg 没有字幕和文字滤镜** | 每条都要人在剪映里打开导出；Mac 能否用【待验证】；新版剪映草稿是加密的，读模板受限（pyJianYingDraft 说明） |
| 要先解决 | 字怎么印到画面上：① 换一个带 libass、freetype 的 ffmpeg（Homebrew 第三方源或静态编译版，要下载）；② 用 Pillow 把字画成透明图片再叠加（新增 Python 依赖）；③ 用 dyhub 已经带着的 Chrome 离屏渲染（hotclip 的做法，最灵活也最复杂） | 在用户的 Mac 剪映上实测：生成的草稿能否打开、导出 |

建议先做 A 的核心几项（竖屏布局、标题、动态字幕、笑点推近），同时用 B 做一个小实验，确认 Mac 剪映的兼容性。两条路共用同一份剪辑方案 JSON。

## 六、建议的优先级

| 优先级 | 内容 | 原因 |
|---|---|---|
| P0 | 竖屏布局（摄像头上、游戏下，或居中加模糊背景）、标题贴片、动态字幕（关键词高亮） | 不做这三样，片子在抖音上就不像成片；数据都有了（逐句稿、标题、笑点句） |
| P1 | 笑点推近、开场钩子（闪现或前置）、笑点音效 | 最能"博眼球"；时机由我们已有的笑声 / 音量 / 笑点句给出 |
| P2 | 封面、发布文案、一片多版、剪映草稿导出 | 发布环节用 |
| 不做 | AI B-roll、AI 配音解说 | 不适合直播切片；涉及 AIGC 标注 |

## 七、待验证和风险

- 【待验证】本机 ffmpeg 9.0.2（Homebrew 官方瓶装版）的编译配置里只有 libx264，没有 libass、freetype，所以 `subtitles`、`drawtext` 滤镜都不能用（EVO-002 就是因此改用彩色边框）。要先选定第五节的三种办法之一。
- 【待验证】pyJianYingDraft 说明里写着"Linux/MacOS 支持草稿生成，但生成的草稿仍然需要在 Windows 版剪映下导出"，Mac 版剪映能不能直接用，要实测。
- 【待验证】摄像头小窗位置检测：clips-studio 用"谁在跟着声音说话"来识别主播的脸，我们没有现成模型；也可以先让 GLM 在九宫格上指出小窗位置，或者每个主播手动配置一次。
- 风险：包装过度（音效太多、推近太频繁）显得廉价，参数要做成可配置项，并请用户看片对比。
- 风险：音效素材、BGM 的版权，以及 AI 生成内容的标注义务。
